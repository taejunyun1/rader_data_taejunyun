# Research Radar 대량 착즙·한계 테스트 설계

- 작성일: 2026-08-28
- 대상: `radar.taejunyun.com`
- 테스트 사용자: `taejun.foto@gmail.com`
- 범위: 착즙(Distill) 입력량, 병렬 처리, 출력 길이, 비용, 장애 복구, UI 지속성, 품질 한계
- 상태: 구현 전 설계안

## 1. 목적

다음 네 가지 질문을 실제 데이터와 실제 OpenAI 비용을 사용해 검증한다.

1. 아주 많은 자료로 착즙을 실행하면 시스템이 어떻게 동작하는가.
2. 자료량이 증가할 때 선택·분할·요약·통합 단계와 처리 시간이 어떻게 변하는가.
3. 자료량이 증가하면 결과의 본문과 근거가 얼마나 길어지며, 길이 증가가 품질 향상으로 이어지는가.
4. 한 번에 약 3~5달러를 사용하는 실제 대량 착즙이 비용 상한 안에서 완료·중단·복구되는가.

이 테스트는 단순히 비용을 소진하는 부하 시험이 아니다. 대량 자료를 읽고 분석하고 다시 분류하는 Research Radar의 핵심 가치가 자료량 증가에도 유지되는지를 확인한다.

## 2. 현재 기준선

현재 착즙은 저장소 전체를 모델에 전달하지 않는다.

- 최근 키워드·질문·사용자 판단을 기준으로 자료를 선별한다.
- 일반 선택 자료는 최대 12개이며, semantic resurfacing을 포함하면 최대 약 14개다.
- 모델에 전달되는 context는 최대 26,000자다.
- 기본 착즙 출력은 키워드 5~7개, 생각 3~5개, 질문 약 3개 등 고정된 구조다.
- Counter를 끄면 2회, 정상 Counter를 포함하면 4회, Counter 재작성까지 발생하면 최대 6회의 모델 호출이 직렬 실행된다.
- Workflow 실행 단계는 현재 15분 timeout을 사용한다.
- 월 AI 예산은 기본 10달러이며, 80% 경고·100% 차단 정책을 사용한다.

따라서 현재 구현에서는 저장소가 100개에서 10,000개로 증가해도 모델 입력량과 출력 길이가 선형 증가하지 않는다. 증가하는 것은 후보 집합과 선별 난이도다. 실제 3~5달러 규모의 단일 착즙을 검증하려면 별도의 Bulk Distill 시험 경로가 필요하다.

관련 코드:

- `worker/src/distill/context.ts`
- `worker/src/distill/run.ts`
- `worker/src/distill/prompts.ts`
- `worker/src/workflows/researchJob.ts`
- `worker/src/lib/openai.ts`

## 3. 테스트 전략

세 가지 시험을 분리한다.

### 3.1 A — 현재 구조 포화 시험

현재 프로덕션 로직을 변경하지 않고 저장소 크기만 늘린다.

검증 대상:

- 전체 자료 수가 늘어도 선택 자료와 context 상한이 지켜지는가.
- 다수 주제가 소수 주제를 밀어내지 않는가.
- 오래된 자료, 사용자 표시 자료, 개인 작업이 계획한 우선순위로 선택되는가.
- D1 선택 쿼리와 semantic search 지연이 어느 지점부터 증가하는가.
- 동일한 입력으로 반복했을 때 선택 결과와 비용이 안정적인가.

이 시험은 현재 제품의 실제 한계를 알려주지만, 3~5달러 단일 실행은 만들지 않는다.

### 3.2 B — 실제 3~5달러 Bulk Distill 시험

대량 원문을 여러 청크로 나누어 읽고 계층적으로 통합하는 시험 전용 경로를 사용한다.

```text
자료 집합 고정
  → 토큰 수 산정·비용 예약
  → 원문 청크 분할
  → 청크별 병렬 독해(Map)
  → 주제별 중간 통합(Reduce 1)
  → 전체 통합(Reduce 2)
  → Critic + Counter 초안
  → 반론 정합성 검증·필요 시 1회 수리
  → 결과·근거·비용 원장 저장
```

이 시험이 자료량에 따른 실제 소화 과정과 출력 품질을 검증하는 주 시험이다.

### 3.3 C — 기존 착즙 반복 Soak 시험

기존 착즙을 여러 번 병렬·반복 실행해 총 3~5달러를 사용한다.

검증 대상:

- 동시 실행과 중복 클릭 방지
- OpenAI RPM/TPM 제한 대응
- Workflow 생성·재시도·완료 처리
- 비용 원장과 월 예산 경계
- Job Center와 페이지 이동 후 진행 상태

이 시험은 운영 안정성 검증용이며, 하나의 대량 자료를 읽는 품질 시험으로 해석하지 않는다.

## 4. 권장 실행 순서

1. A 시험으로 현재 기준선과 선택 포화 지점을 측정한다.
2. 비용 없는 dry-run으로 Bulk Distill 예상 토큰·호출 수·가격을 계산한다.
3. 실제 최대 0.25달러 pilot을 실행한다.
4. pilot이 모든 통과 조건을 만족하면 3달러 시험을 한 번 실행한다.
5. 3달러 시험의 비용·복구·품질이 정상일 때만 5달러 시험을 실행한다.
6. C 시험으로 동시성·중복·예산 race condition을 검증한다.
7. 결과를 보고서로 고정하고 테스트 자료를 별도 확인 후 정리한다.

## 5. 테스트 데이터 설계

문서 개수만으로 비용을 정하지 않는다. 문서마다 길이가 다르므로 정규화된 입력 토큰 수와 실제 사용량을 기준으로 한다.

| 등급 | 정규화 입력량 | 목적 |
|---|---:|---|
| S | 100K tokens | 분할·기본 복구 검증 |
| M | 500K tokens | 병렬 처리·중간 통합 검증 |
| L | 1M tokens | 계층 통합·주제 보존 검증 |
| XL | 2M tokens | 장시간 실행·체크포인트 검증 |
| Cost-3 | 실측 3달러 상한 | 실제 비용 한계 시험 |
| Cost-5 | 실측 5달러 상한 | 최종 한계·강제 중단 시험 |

자료 구성은 다음 축을 교차한다.

- 긴 자료 소수 대 짧은 자료 다수
- PDF·웹·메모·개인 작업·학술 논문
- 한국어·영어·혼합 언어
- 최신 자료 대 오래된 resurfaced 자료
- 중심 주제 70% 대 소수 주제 30%
- 정상 텍스트·빈 텍스트·깨진 인코딩·중복 자료
- 정상 원문 대 프롬프트 공격 문장을 포함한 원문

### 5.1 운영 데이터 격리

- 모든 테스트 자료와 세션에 고유한 `testRunId`를 부여한다.
- R2는 `load-tests/<testRunId>/` prefix를 사용한다.
- D1 자료는 운영 통계와 Radar에 섞이지 않도록 테스트 scope로 조회를 제한한다.
- 실제 사용자 표시·발전시키기 기록을 테스트가 변경하지 않는다.
- 테스트 종료 후 결과 JSON·원장·로그를 먼저 export한다.
- 테스트 데이터 삭제는 목록과 export 경로를 확인한 뒤 별도 승인으로 수행한다.

## 6. Bulk Distill 처리 설계

### 6.1 입력 스냅샷

실행 시작 시 자료 ID, version ID, 원문 hash, 글자 수, 예상 토큰 수를 고정한다. 실행 중 자료가 변경되어도 해당 run은 최초 스냅샷을 사용한다.

### 6.2 청크 분할

- 제목·출처·문단 경계를 보존한다.
- 하나의 청크는 약 6K~10K 입력 토큰을 목표로 한다.
- 중첩은 필요한 문단에만 최소 적용한다.
- 청크마다 source/version/page/section provenance를 보존한다.
- 빈 청크와 동일 hash 청크는 모델 호출 전에 제외한다.

### 6.3 병렬 Map

- 기본 동시성은 4로 제한한다.
- Cloudflare의 동시 outbound connection 여유를 남긴다.
- 각 청크는 독립 idempotency key를 사용한다.
- 결과는 Workflow step payload에 크게 누적하지 않고 R2에 저장한 뒤 참조만 반환한다.
- 실패한 청크만 재시도하며 완료 청크를 다시 결제하지 않는다.

### 6.4 계층 Reduce

- 청크 요약 6~10개를 하나의 주제 묶음으로 통합한다.
- 중간 통합은 기본 모델을 사용한다.
- 최종 통합·Critic·Counter 검증은 상위 모델을 사용한다.
- 그룹 수가 많으면 Reduce 단계를 반복하되 깊이와 비용을 사전에 계산한다.
- 최종 통합 입력은 모델 context 상한의 70% 이하로 유지한다.

### 6.5 병렬화 경계

병렬 실행:

- 서로 독립적인 청크 Map
- 서로 독립적인 주제별 Reduce
- 최종 Distill 이후 Critic과 Counter 초안

직렬 실행:

- 입력 스냅샷 이후 청크 생성
- Map 완료 이후 Reduce
- 최종 통합 이후 검증
- Counter 검증 실패 이후 수리와 재검증

품질 의존성이 있는 단계를 억지로 병렬화하지 않는다.

## 7. 출력 길이 정책

자료량에 따라 본문을 선형 증가시키지 않는다. 읽기 가능한 본문과 확장 가능한 근거 부록을 분리한다.

### 7.1 본문

- 핵심 서사와 주요 판단은 입력량과 무관하게 일정한 읽기 길이를 유지한다.
- 목표 길이는 약 2,000~4,000 한국어 단어 또는 동등 분량으로 제한한다.
- 키워드·질문·연구 방향의 항목 수는 필요에 따라 완만하게 증가하지만 최대치를 둔다.

### 7.2 근거 부록

- 자료량이 늘면 source coverage와 근거 부록이 증가한다.
- 각 핵심 주장에 대표 provenance를 연결한다.
- 동일한 주장을 지지하는 중복 근거는 묶는다.
- 부록은 최대 길이를 넘으면 주제별 별도 파일로 분리한다.

### 7.3 검증할 가설

- 전체 자료량이 10배가 되어도 본문 길이는 2배를 넘지 않는다.
- 근거 부록의 source coverage는 자료량에 따라 증가한다.
- 길이 증가보다 미지원 주장 감소와 소수 주제 보존이 우선이다.

## 8. 비용 통제

### 8.1 사전 추정

실행 전에 다음을 표시한다.

- 총 입력 토큰 예상치
- Map·Reduce·검증 호출 수
- 모델별 예상 입력·출력 비용
- 최저·예상·보수적 최대 비용
- 월 잔여 예산

### 8.2 예약과 상한

- Distill도 Deep Analysis와 동일하게 실행 전 비용을 예약한다.
- 3달러 시험은 hard cap 3달러, 5달러 시험은 hard cap 5달러를 사용한다.
- 월 잔여 예산이 `시험 상한 + 10% 안전 여유`보다 작으면 시작하지 않는다.
- 누적 실측 비용과 남은 단계의 보수적 예상 비용이 상한을 넘으면 새 호출을 시작하지 않는다.
- 이미 시작된 한 호출의 비용은 완전히 차단할 수 없으므로 최대 한 호출 비용을 headroom으로 예약한다.
- 중단 시 완료된 Map·Reduce 결과를 보존하고 `PARTIAL_BUDGET_STOP`으로 종료한다.

### 8.3 가격 기준

기본 기준 모델은 현재 역할 설정을 사용한다.

- 기본 모델: `gpt-5-mini`
- 상위 통합·검증 모델: `gpt-5.4-mini`

가격은 실행 직전 등록된 `MODEL_PRICING_JSON`과 OpenAI 공식 가격을 대조한다. 가격 미등록 모델은 한계 시험에 사용하지 않는다.

OpenAI 공식 참고:

- https://developers.openai.com/api/docs/models/gpt-5-mini
- https://developers.openai.com/api/docs/models/gpt-5.4-mini

## 9. 핵심 한계 테스트 행렬

### 9.1 자료량·선택 포화

| 케이스 | 입력 | 확인 항목 |
|---|---|---|
| V1 | 10 sources | 기준 결과 |
| V2 | 100 sources | 선택 상한·지연 |
| V3 | 1,000 sources | 편향·다양성 |
| V4 | 10,000 sources | D1·semantic search 포화 |
| V5 | 25.9K/26.0K/26.1K chars | context 경계 |

### 9.2 구성 차이

- 같은 토큰량에서 긴 자료 10개 대 짧은 자료 1,000개
- 개인 작업 10%·30%·50%
- 중심 주제 90% 대 소수 주제 10%
- 신규 자료 위주 대 오래된 resurfacing 위주
- 중복률 0%·30%·70%

### 9.3 병렬·중복 실행

- 동일 버튼 연속 10회 클릭
- 동일 입력 3개 동시 요청
- 서로 다른 입력 3개·10개 동시 요청
- Counter on/off가 다른 요청 동시 실행
- 월 예산 95% 이상에서 여러 작업 동시 시작

예산 확인과 실제 결제 사이 race condition을 반드시 검증한다. 현재 Distill에는 Deep Analysis와 같은 선예약이 없으므로 우선 보강 대상이다.

### 9.4 장애 주입

각 모델 단계에 다음 장애를 주입한다.

- HTTP 429
- HTTP 500/502/503
- 응답 지연과 15분 timeout
- 연결 중단
- 빈 응답
- 잘린 JSON·잘못된 JSON
- usage 필드 누락
- AI 호출 성공 후 비용 정산 실패
- D1 저장 성공 후 Workflow 응답 실패
- Workflow 재시작·중복 전달

### 9.5 보안·내용 오염

- 원문 안의 시스템 지시 위장 문장
- JSON 구조를 닫으려는 문자열
- 과도한 반복·토큰 폭탄
- HTML/script 잔재
- 존재하지 않는 논문·작가를 제안하도록 유도하는 문장
- Counter가 직접 반대가 아니라 약한 보완이나 strawman으로 흐르는 사례

### 9.6 UI 지속성

- 착즙 중 다른 메뉴로 이동
- 새로고침
- 새 탭에서 동일 계정 접속
- 브라우저를 닫았다가 재접속
- 여러 작업 동시 진행
- 완료·부분 완료·실패·비용 중단 상태
- Job Center에서 결과 페이지로 이동

진행률은 뒤로 가지 않아야 하며, 페이지 상태가 아니라 서버의 job 상태를 기준으로 표시해야 한다.

### 9.7 플랫폼 한계

- Workflow step 결과 1MiB 초과 방지
- Workflow 상태 크기 증가 방지
- 기본 subrequest 한계 확인
- Worker 128MB 메모리 한계 확인
- D1 단일 DB write queue와 overload 확인
- D1 row 2MB 한계 확인
- Workflow CPU 30초 기본값과 현재 15분 step timeout 확인
- 큰 결과와 청크는 R2에 저장하고 Workflow·D1에는 참조만 저장

## 11. 통과 기준

### 필수

- 동일 입력 중복 클릭으로 생성되는 활성 job은 1개다.
- 재시도 때문에 같은 모델 응답이 중복 결제되지 않는다.
- 완료·실패·차단 작업은 모두 terminal 상태로 남는다.
- 3달러 시험은 3달러 상한과 한 호출 headroom 안에서 멈춘다.
- 5달러 시험은 3달러 시험이 통과한 뒤에만 시작한다.
- 운영 자료와 테스트 자료가 통계·Radar·사용자 판단에서 섞이지 않는다.
- 페이지 이동·새로고침 후에도 서버 작업은 계속된다.
- 출력의 핵심 주장 95% 이상이 provenance 또는 명시적 synthesis로 구분된다.
- 프롬프트 공격에 의해 시스템 출력 형식이나 정책이 변경되는 사례는 0건이다.

### 권장

- 예상 비용과 실측 비용 차이는 15% 이하다.
- hard cap 초과액은 0.15달러 이하이며 원인이 한 건의 in-flight 호출로 설명된다.
- C 반복 Soak 시험에서 정상 입력 작업의 완료율은 95% 이상이다.
- unsupported claim 비율은 5% 이하다.
- 전체 자료량 10배 증가 시 본문 길이는 2배를 넘지 않는다.
- 소수 주제 10% fixture가 최종 결과 또는 근거 부록에서 완전히 소실되지 않는다.

## 12. 관찰된 선행 위험

1. 현재 Distill은 실행 전 비용 예약을 하지 않으므로 동시 실행 시 월 예산을 넘을 수 있다.
2. 전체 Distill이 하나의 Workflow `step.do` 안에서 실행되어 단계별 체크포인트·부분 재시도가 약하다.
3. 모델 호출은 논리 의존성 때문에 대부분 직렬이며, 대량 입력 처리 구조가 없다.
4. session ID가 실행 중 생성되므로 D1 저장 이후 step 결과 반환 전에 실패하면 중복 세션 가능성을 시험해야 한다.
5. context selection이 상위 키워드와 최근 신호 중심이어서 대규모 저장소에서 소수 주제를 소실할 수 있다.
6. 고정 출력 schema 때문에 자료량 증가가 근거 coverage 증가로 이어지지 않을 수 있다.

위 위험을 고치지 않은 상태에서도 A와 C 시험은 가능하지만, B 시험은 비용 예약과 단계 체크포인트를 먼저 구현해야 한다.

## 13. 산출물

각 실행은 다음 파일을 남긴다.

- `manifest.json`: 자료·version·hash·토큰량
- `cost-estimate.json`: 단계별 예상 비용
- `usage-actual.json`: 실제 모델 usage와 비용
- `timings.json`: 단계별 시간·재시도
- `selection.json`: 후보와 최종 선택 이유

- `report.md`: 통과·실패·후속 조치

## 14. 구현 순서

### Phase 0 — 계측 보강

- per-run cost estimator
- Distill 비용 선예약
- testRunId와 테스트 scope
- 단계별 timing·token·retry 지표
- hard cap과 부분 완료 상태

### Phase 1 — 현재 구조 포화 시험

- synthetic fixture 생성
- 10/100/1,000/10,000 source 시험
- 선택·지연·편향 기준선 보고서

### Phase 2 — Bulk Map/Reduce 시험 경로

- 입력 스냅샷과 토큰 산정
- 청크 저장·병렬 Map
- 계층 Reduce
- Critic·Counter·검증
- R2 결과 참조와 재개

### Phase 3 — 장애·동시성 시험

- 모델·D1·Workflow fault injection
- 중복 클릭과 예산 race
- 재시도·정산·세션 중복 검증

### Phase 4 — 실제 비용 시험

- 0.25달러 pilot
- 3달러 시험
- 조건부 5달러 시험

### Phase 5 — 결과 정리

- 기준선과 Bulk 결과 비교
- 비용 대비 source coverage·품질 분석
- 운영 권장 상한 결정
- export 후 테스트 데이터 정리 승인

## 15. 비목표

- 모든 저장소 자료를 매번 무조건 모델에 전달하지 않는다.
- 본문을 자료량에 선형 비례해 무한히 늘리지 않는다.
- 가격 미등록 모델로 실제 한계 시험을 실행하지 않는다.
- 테스트를 이유로 월 예산 guardrail을 제거하지 않는다.
- 테스트 데이터를 운영 Radar와 사용자 연구 판단에 섞지 않는다.
- 실패한 대량 실행을 처음부터 전부 다시 결제하지 않는다.

## 16. 최종 권장안

`A 현재 구조 포화 → 0.25달러 pilot → B 3달러 Bulk Distill → C 동시성 Soak → 조건부 5달러 Bulk Distill` 순서로 진행한다.

이 순서가 현재 제품의 실제 한계를 먼저 확인하면서도, 실제 비용을 사용한 대량 소화 품질과 운영 안정성을 모두 검증하는 가장 안전한 경로다.
